# CoursePilot 选课领航 · 数据库设计与规范化

> 经管实践调研演讲初稿
> 项目：上海交通大学安泰经济与管理学院 · 金融学专业个性化选课助手

---

## 1. 项目一句话

不是"帮你抢课"的工具，而是把选课从一次拼手速的操作，重构成一条**有预案、可执行、能复盘**的时间线：选课前生成 3 套可解释的个性化课表预案，选课中处理冲突/满员/备选，选课后沉淀真实反馈回流修正课程画像。

**合规边界**：不自动登录、不自动提交、不高频轮询——系统追求的不是"比别人快"，而是"更不失败"。

## 2. 系统已实现的核心功能（演示入口 http://127.0.0.1:8765）

| 阶段 | 功能 |
|---|---|
| 选课前 | 培养计划解析、毕业学分进度、五维课程打分（兴趣/负荷/给分/教师/难度）、束搜索生成 Top-3 课表、Pareto 权衡图、自然语言偏好解析（"周三下午有实践，想学数据分析"→ 禁排时段 + 兴趣标签） |

| 真实数据 | jCourse 选课社区评价只读接入（均分、评分人数、原文），不影响推荐评分 |

## 3. 数据存储现状：三个"数据库"，只有一个是真的

| 存储 | 形态 | 内容 |
|---|---|---|
| `backend/data/seed.json` | 单 JSON 文档（只读） | 课程、教学班、培养计划、学期配置 |
| `backend/data/students/*.json` | 每学生一个 JSON 文档 | 档案、草稿、对话、偏好反馈、解析证据 |
| `backend/data/auth.sqlite3` | SQLite（2 张表） | 用户口令散列、登录会话 |

**现状的问题**：

1. 多值属性（标签、先修、时段、已修课程……）全部平铺在 JSON 数组里，**不满足 1NF**
2. 跨存储的关联（用户→学生、反馈→课程）**没有任何外键约束**，引用完整性靠运气
3. 存在传递依赖：`教学班 → 教师 → 教师评分`；`培养计划.module` 与 `课程.category` 完全冗余
4. 换专业/学期只能整体替换 seed.json，无法多学期并存

（此处展示旧版 ER 图：`er-1-参考库.png` / `er-2-学生与认证.png` / `er-3-全局关系.png`）

## 4. 规范化到 BCNF：每一步拆了哪张表、消除了什么依赖

### 4.1 第一范式（1NF）

把所有多值属性拆成独立从表：

- `COURSE.tags / prereqs` → `COURSE_TAG(code, tag)`、`PREREQ(code, prereq_code)`
- `OFFERING.sessions[]` → `SESSION(offering_id, day, start, end, location)`（弱实体，复合主码）
- `profile.assessment{}` → `ASSESSMENT(code, component, weight)`
- 学生档案的 `completed / interests / locked / excluded / blocked / affinity` → 各一张二列从表

### 4.2 第三范式（3NF）：消除三处传递依赖

| 传递依赖 | 处理 |
|---|---|
| `OFFERING.id → teacher → teacher_rating` | 拆出 `TEACHER(name, rating)`，教学班只留外键 |
| `PLAN_ITEM.code → module`（与 `COURSE.category` 冗余） | 删除 `module` 列——迁移前用数据验证过 16 条记录完全一致 |
| `TERM_CONFIG → major → college` | 拆出 `MAJOR(name, college)` |
| `FEEDBACK.course → tags`（快照冗余） | 删除 `tags` 列，用时 JOIN |

### 4.3 BCNF

逐表验证：所有非平凡函数依赖的决定因素都是超码。拆分后 **28 张表全部满足 BCNF**；学生侧多值属性一列一表，同时达到 4NF。

（此处展示 BCNF 版 ER 图：`er-bcnf-1-参考库.png` / `er-bcnf-2-学生与认证.png` / `er-bcnf-3-全局关系.png`）

### 4.4 额外的结构改进

- `COURSE_PROFILE`（难度/给分/周投入等画像数据）与 `COURSE`（教务事实）分表：来源、更新频率、置信度完全不同，画像带 `sample_size + confidence`，为"后期反馈回写修正画像"的闭环预留结构

## 5. 迁移过程中发现的三个真实数据问题

> 这些问题在原 JSON 存储里**没有任何机制能发现**——是外键约束在迁移时主动报出来的：

1. **悬空先修引用**：`FI3101 公司金融` 的先修课 `ACC2101` 不在课程表中（先修课是低年级课程，不在本学期开课列表）。处理：`prereq.prereq_code` 不加外键并显式标注
2. **消息主码撞车**：问答两条消息共享同一时间戳，`(student_id, time)` 不是真主码 → `MESSAGE` 主码补充 `seq` 序号
3. **注册即悬空**：注册账号时不生成学生档案，`users.student_id` 指向不存在的档案 → 迁移时补占位行保住外键，后端逻辑也已明确记录

## 6. 迁移与验证

- 迁移脚本 `backend/db/migrate.py`：`seed.json` + 8 份学生 JSON + `auth.sqlite3` → 统一 SQLite 关系库 `data/coursepilot.db`
- **往返一致性校验**：用 SQL 重建原始 JSON 逐字段 diff——参考库完全一致；8 份学生文档 × 16~21 项（档案/草稿/多值/消息/证据）全部一致
- `PRAGMA foreign_key_check` 通过
- 同一 schema 已导入本机 **PostgreSQL**（数据库名 `coursepilot`，31 张表），可用 pgAdmin 直接查询

```sql
-- 示例：教学班全景
SELECT o.id, c.name, o.teacher, t.rating, o.capacity, o.enrolled
FROM offering o
JOIN course c  ON c.code = o.code
JOIN teacher t ON t.name = o.teacher;
```

## 7. 当前边界（诚实声明）

- **运行中的网站仍使用原 JSON 存储**，SQL 库是分析/展示用的一致快照，后端切换（`SqliteStudentRepository` 替换 JSON 读写层、API 保持不变）是下一步工作
- 课程难度/负荷/给分为演示数据，正式使用需真实调研数据替换
- `OUTCOME_HISTORY`（选课结果回写）与历史中签率表结构已预留，等待真实数据

## 8. 后续路线

1. 后端数据访问层切换到关系库（接口不变）
2. 接入真实培养计划与开课数据
3. 海选志愿梯度优化（依赖历史中签率数据）
4. 学习反馈匿名聚合 → 画像回写闭环
