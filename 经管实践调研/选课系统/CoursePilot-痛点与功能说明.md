# CoursePilot 选课领航 · 三阶段能力框架

> 上海交通大学安泰经济与管理学院 · 金融学专业演示系统
> 本文按**选课前期 / 中期 / 后期**重排系统框架，既包含已落地能力，也包含规划中的能力，状态逐项标注。

---

## 0. 阅读说明

**项目定位**：不是"帮你抢课"的工具，而是把选课从一次拼手速的操作，重构成一条有预案、可执行、能复盘的时间线。

**状态图例**

| 标记 | 含义 |
|---|---|
| 已实现 | 代码已落地，可在演示系统中操作 |
| 部分实现 | 主流程可用，但数据或覆盖面不完整 |
| 规划中 | 已完成设计，尚未接入 |
| 试点设计 | 已有方案与边界规则，等待真实数据与教师/教务参与 |
| 不做 | 明确排除，见第 3.3 节 |

## 1. 总体框架：一条时间轴，三次价值交付

| 阶段 | 时间窗 | 学生真正的问题 | 系统交付物 | 衡量指标 |
|---|---|---|---|---|
| **前期** | 选课前 2–4 周 | 选什么、值不值、能不能排下 | 3 套个性化课表预案 + 课程画像 | 方案采纳率、修改次数 |
| **中期** | 海选 / 抢选 / 补退选 | 会不会冲突、满了怎么办、会不会白选 | 可执行清单 + 备选路径 | 冲突率、选课完成率 |
| **后期** | 开学到期未 | 这门课到底怎么样、下次怎么选得更好 | 学习反馈 + 画像回写 | 评价样本量、负荷预估误差 |

三个阶段不是并列的三个模块，而是一个**闭环**：后期的真实负荷与评价，应该回流去修正前期的课程画像和个人模型。当前系统中这条回流链路是**规划中**，也是下一阶段最值得做的事。

## 2. 选课前期：把"信息"和"决策"做对

### 2.1 痛点

- **信息分散**：培养计划是 PDF，开课信息在教务网，课程难度在选课社区和长帖里，老师风格在学长口口相传中，学生要在多个系统之间手工拼图。
- **口径不一致**：同一门课，社区说的难度、大纲写的考核、学长记忆里的给分经常对不上，学生不知道信哪个。
- **决策是多目标问题**：时间冲突、先修、模块学分、保研/出国 GPA 策略、作息偏好同时约束，人脑不擅长这类组合优化。
- **试错成本极高**：一门课选错，代价是 16 周，且中途退出的成本同样很高。
- **经验不可复用**：往届经验散落在群聊，一学期后刷走，下一届从零开始踩同样的坑。

### 2.3 前期最关键的两个设计判断

**第一，AI 不做决定，只产出可解释的候选集。**
每套方案都给出"为什么是这套""需要注意什么"；每门课都能展开五维贡献条，看到它的分数是怎么来的。选课包含大量价值判断（有人愿意为一门好课降 0.1 GPA），模型一旦越权替用户拍板，信任会一次性崩塌。

**第二，用平均效用而不是总分。**
如果目标函数是效用总和，算法会为了凑学分把课表塞满；改成平均效用并叠加超负荷惩罚，才会真正比较"这门课值不值得占一个位置"。这是求解器里最重要的一次修正。

### 2.4 前期的交付物

不是一张课程列表，而是**一套选课预案**：3 套可切换的课表 + 每门课的依据 + 每套方案的代价说明 + 一张权衡图。学生带着这份预案进入选课周，而不是当天现场发挥。

## 3. 选课中期：把"执行"做稳，而不是做快

### 3.1 痛点

- **窗口极短**：海选与抢选窗口只有几十分钟，容错空间几乎为零。
- **系统不可控**：页面卡顿、提交超时、验证码反复，失败与学生个人能力无关。
- **名额瞬时变化**：心仪班次可能在两次刷新之间就被占满，原方案当场失效。
- **冲突后知后觉**：很多冲突要到真正提交时才暴露，此时已来不及补救。
- **计划外约束**：某个下午临时有实践、实验课或社团活动，前期课表直接作废。
- **失败无从复盘**：为什么没选上、下次该怎么调整，几乎没有数据可依。

### 3.2 能力清单

| # | 能力 | 说明 | 状态 | 代码位置 |

| 1 | 冲突预检 | 选课前就验证时间冲突，而不是到系统里才发现 | 已实现 | `solver.py` 位图冲突检测 |
| 2 | 禁排时段 | 手工或自然语言设置"这个时段不能上课"，求解时直接排除 | 已实现 | `solver.py`、`App.tsx` |
| 3 | 锁定课程 | 固定某门课，其余课程围绕它重排 | 已实现 | `solver.py` |

| 5 | 备选预览与采用 | 明确列出"移出哪些班、加入哪些班"，确认后才生效 | 已实现 | `App.tsx` |
| 6 | 撤销操作 | 回滚本次改动，保留此前的满员记录 | 已实现 | `App.tsx` |

### 3.3 关于"抢课加速"的边界

这是整个项目里唯一"技术上完全做得到、但绝对不能做"的部分，必须写清楚。

**为什么不做外挂**

1. **校规层面**：使用外挂程序、扰乱选课秩序，属于学生手册中网络与信息系统使用规定的禁止项。
2. **法律层面**：绕过认证或技术保护措施批量访问教务系统，可能触及《刑法》第 285、286 条与《网络安全法》第 27 条。
3. **公平层面**：选课是零和分配。外挂把"手速竞争"升级为"工具竞争"，一旦普及，所有人被迫使用，最终没有人变快，只是所有人更焦虑。
4. **工程层面**：教务系统的峰值容量是为人类操作设计的，高频请求会让它雪崩——包括发起者自己的请求。

**合规的"快"是什么**

不是绕过限制，而是减少失败：冲突提前验证、班次已满提前知道、备选路径提前准备好、操作步骤压到最少。本质上是**"更不失败"**，而不是"比别人更快"。

**唯一合法的加速路径**

与教务处共建：官方接口 + 授权客户端 + 令牌桶配额。学校得到可观测的流量与削峰入口，学生得到稳定的提交体验。这条路在方案里不是软性建议，而是中期能力真正落地的前提。

## 4. 选课后期：把"经验"留下来

### 4.1 痛点

- **体验留不下来**：每周真实投入多少小时、哪里最难、给分如何，只存在于个人记忆和群聊。
- **反馈到不了教师**：学生有意见但缺渠道，教师也看不到结构化的学情分布。
- **评教数据沉睡**：教务处的评教以自由文本为主，难以聚合成可用结论。
- **供需错配无人看见**：哪些课该扩班、哪些该停开，缺少数据支撑。
- **个人模型不更新**：这学期高估或低估了自己的负荷承受力，下学期仍按老经验选课。

### 4.2 能力清单

| # | 能力 | 说明 | 状态 |
|---|---|---|---|
| 1 | 学习过程轻量记录 | 每周 30 秒：实际投入时长、掌握度自评、卡住的知识点 | 规划中 |
| 2 | 匿名聚合 | 每个展示单元至少 5 名独立参与者才展示，稀疏单元隐藏 | 试点设计 |
| 3 | 负荷分布与高峰 | 教师端查看每周负荷分布与作业高峰，只给教学参考 | 试点设计 |
| 4 | 教师反馈闭环 | 教师主动开启才收到报告，且承诺不用于考核与排名 | 试点设计 |
| 5 | 期末复盘与画像回写 | 用真实成绩与投入修正课程画像，跨学期衰减 | 规划中 |
| 6 | 个人模型校准 | 对比"预估负荷"与"实际负荷"，修正个人承受力参数 | 规划中 |
| 7 | 教务驾驶舱 | 意向课程的时段冲突、先修不满足、学生报告满班、扩班依据 | 试点设计 |

### 4.3 后期的伦理边界

| 规则 | 说明 |
|---|---|
| 匿名聚合 | 教师端只看分布，永不显示个体 |
| 最小样本量 | 少于 5 名独立参与者不展示 |
| 教师主动开启 | 不开启则数据只用于学生端负荷预警 |
| 不进考核 | 协议层面承诺不用于评优、晋升、排名 |
| 只报问题不报人 | 报告形态是"第 3 章理解困难占比 61%"，不是"某老师讲得不好" |
| 可撤回 | 学生可删除自己的记录 |

## 5. 贯穿三阶段的底座

### 5.1 数据契约

`backend/data/seed.json` 是唯一数据入口，包含：培养计划、模块学分要求、毕业学分、已修记录、课程、教学班、学生默认档案。替换这个文件即可换专业、换年级、换学期。

真实数据目前只有一类：**选课社区（jCourse）的均分、评分人数与评价原文**，通过 `JCOURSE_API_KEY` 只读接入，且**不写入课表、不改变推荐评分**。

### 5.2 算法

- **单课打分**：五维（兴趣、负荷、给分、教师、难度匹配）+ 早八惩罚 + 中签风险偏好，权重由三个滑杆决定。
- **组合求解**：按"必修 → 专业选修 → 通识"分阶段束搜索；时段位图做 O(1) 冲突检测；模块边界强制最低学分。
- **多样性**：Top-K 之间用 Jaccard 相似度去重，避免三套方案长得一样。
- **权衡**：所有可行解投影到"周投入 × 期望学分"平面，画非支配边界。

### 5.3 合规原则

不自动登录、不自动提交、不做多账号、不做验证码识别、不做高频轮询。官网选课由本人完成，系统只提供预案、清单与提示。

## 6. 路线图

| 阶段 | 已完成 | 下一步 | 前置条件 |
|---|---|---|---|
| 前期 | 画像、五维打分、Top-3 课表、方案对比、敏感度滑杆、自然语言偏好 | 海选志愿梯度优化、多学期规划、画像自动抽取 | 历史中签数据、真实培养计划 |
| 中期 | 冲突预检、禁排、锁定、满员、备选、撤销、换班次、清单导出 | 端侧预填与一键提交、候补提醒 | 与教务处达成授权 |
| 后期 | 匿名聚合规则、最小样本量、教师 opt-in 设计 | 轻量打卡、教师端、教务看板、画像回写 | 真实数据 + 教师参与 |

**如果只能先做一件事**：把"海选志愿梯度"做出来。它不碰任何敏感接口，只需要一份历史中签率（哪怕手工整理），但对安泰学生而言，海选阶段的焦虑远大于抢选阶段——因为海选拼的是策略，而策略是可以用数据优化的。

## 7. 已知局限

1. **求解失败 ≠ 数学无解**：采用有限宽度束搜索，搜索失败只说明当前束宽下没找到可行解。
2. **演示数据不代表真实开课**：课程难度、周投入、给分均为示例值，需真实调研数据替换。
3. **社区数据覆盖不均**：小样本课程不展示聚合分，部分课程只能看原文；缺少密钥或限流时功能不可用。
4. **本地模型可选**：未配置 Ollama 时自然语言解析退化为关键词与时段规则，复杂表达可能识别不全，因此保留人工修正步骤。
5. **教务侧能力为试点设计**：教师端与教务看板尚未接入真实数据，不能当作已交付功能对外表述。
